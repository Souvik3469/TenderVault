TenderVault — Deep Dive A multi-role B2B tender platform: companies publish tenders, vendors bid, one bid wins

Two documents, two vintages The Docs/ folder at the repository root (SRS, SPMP, COCOMO, Gantt, DFDs, test-case workbook) is academic coursework describing an earlier version of this system. It does not match the code. This document describes what is actually in the repository.

0. Overview

Procurement, modelled properly. A company publishes a tender with a category, a minimum acceptable amount, and a deadline. Vendors discover it, ask clarifying questions, and submit bids. The company awards exactly one bid; every other bid is rejected in the same atomic operation. An admin can review and rate tenders for quality.

The interesting part is not CRUD — it's that a tender is a state machine with money attached, and awarding is a transaction that must not half-happen.

Layering

backend/src/ ├── app.ts · server.ts ├── v1/ │ ├── routes/ auth · user · tender · admin · notification │ ├── controllers/ thin — parse, delegate, respond │ ├── services/ all business logic (tender.service.ts is 567 lines of it) │ ├── dtos/ request shapes │ ├── middlewares/ auth · validate · upload · error │ └── config/env.ts ├── utils/ AppError · response · notify └── prisma/ 6 models

Controllers are 24–270 lines; services carry the logic. error.middleware catches AppError centrally, so services throw new AppError('...', 403) and never touch the response object. That separation holds consistently across the codebase.

Three actors

User.role — vendor · company · admin. One `User` model with three relations to `Tender`: ownedTenders (as company), boughtTenders (as winning vendor), evaluatedTenders (as reviewing admin).

Now enums (changed 2026-09-15) Every status and role was originally a String with the legal values in a trailing comment, so the guards compared string literals with no compile-time protection against a typo. They are now Prisma enums — UserRole, TenderStatus, BidStatus, NotificationType — with member names identical to the previously stored strings, so documents and API payloads are unchanged.

Worth noting what that surfaced: converting them produced six compile errors that had been latent — untyped status filters flowing into queries in three places, an untyped notification type, and a stale field in a select. None were visible while the values were strings.

2. Tender Lifecycle

draft ──publish──▶ open ──close──▶ closed │ │ │ (deadline) │ └──────────────────┘ │ │ └── award ────▶ awarded (terminal) │ cancel ──▶ cancelled (blocked once awarded)

Transitions are guarded, not assumed

Each transition is a named operation rather than a generic updateStatus(status) — which is what makes preconditions enforceable at all:

export const publishTender = async (tenderId, userId) => {
  const tender = await prisma.tender.findUnique({ where: { id: tenderId } });
  if (!tender) throw new AppError('Tender not found.', 404);
  if (tender.companyId !== userId) throw new AppError('Unauthorized.', 403);
  if (tender.status !== 'draft')
    throw new AppError('Only draft tenders can be published.', 400);
  ...
}

Same shape for closeTender (open only) and cancelTender (anything but awarded). Ownership is checked before state, and both before any write.

Originally the machine existed only as the union of those scattered guards — correct, but with no single place to read the legal transitions, so adding a state meant finding every one of them. As of 2026-09-15 both machines are declared once in src/v1/domain/tender-state.ts, and the five guards call assertTenderTransition / assertBidTransition against that table:

export const TENDER_TRANSITIONS = {
  draft:     [open, cancelled],
  open:      [closed, awarded, cancelled],
  closed:    [awarded, cancelled],
  awarded:   [],   // terminal
  cancelled: [],   // terminal
}

Behaviour is the same or stricter, never looser; the error messages now name the allowed transitions.

Deadline expiry

autoExpireTender runs opportunistically at the start of read paths: if a tender is open and past its deadline, it flips to closed and notifies vendors with pending bids.

Lazy expiry avoids needing a scheduler, but it means a tender nobody looks at stays open past its deadline, and the unlucky first reader pays for the write.

3. Bidding

Vendors submit a Bid carrying an amount and a message — the proposal, not just a number, which is what makes this procurement rather than an auction. Bids move pending → accepted | rejected | withdrawn.

Award & auto-reject — the function worth reading

// 1. authorise and validate state
if (bid.tender.companyId !== userId) throw new AppError('...', 403);
if (bid.status !== 'pending')        throw new AppError('Only pending bids can be accepted.', 400);
if (!['open','closed'].includes(bid.tender.status ?? ''))
                                     throw new AppError('...', 400);

// 2. capture who to notify BEFORE the transaction changes their rows
const othersToReject = await prisma.bid.findMany({
  where: { tenderId: bid.tenderId, id: { not: bidId }, status: 'pending' },
  select: { vendorId: true },
});

// 3. one atomic award
await prisma.$transaction([
  prisma.bid.update({    where: { id: bidId }, data: { status: 'accepted' } }),
  prisma.tender.update({ where: { id: bid.tenderId },
                         data: { status: 'awarded', buyerId: bid.vendorId } }),
  prisma.bid.updateMany({ where: { tenderId: bid.tenderId, id: { not: bidId }, status: 'pending' },
                          data: { status: 'rejected' } }),
]);

// 4. notify only after it commits
Three things this gets right Atomicity — awarding, recording the buyer, and rejecting every other bid either all happen or none do. A partial award would leave losing bids pending against a closed tender.
Pre-capture — the losing vendors are read before the transaction sets them to rejected. Reading after would return an empty set and nobody would be told. That's a subtle ordering bug avoided deliberately.
Side effects after commit — notifications fire once the transaction has succeeded, so nobody is told they lost a tender that was never awarded.

Two sibling functions — closeTender and cancelTender — used to notify before their update committed, so a failed update still told vendors the tender had closed. Fixed 2026-09-15; all three now follow the same order.

4. Q&A

Question → Answer, scoped to a tender, vendor-asked and company-answered (askQuestion rejects non-vendors with a 403). Public clarification threads are a real feature of procurement — a bidder's ambiguity is usually every bidder's ambiguity — and modelling them is what separates this from a generic CRUD marketplace.

5. Notifications

export const notify = (userId: string, body: string, type: string): void => {
  prisma.notification.create({ data: { userId, body, type, read: false } })
    .catch((err) => console.error('[notify]', err));
};

Deliberately never awaited — documented as such — so notification writes never block or fail a request. The trade is explicit: delivery is best-effort, and a failure is a log line nobody reads.

6. Auth

JWT via jose, verified in auth.middleware.ts, with a proper claims payload (payload.id) rather than a bare signed string. The user is loaded per request and attached to req.user through a typed express.d.ts augmentation.

7. What Changed, and What's Still Open

This section used to be a "what I'd do differently" list. Most of it was acted on in 8e77025 (2026-09-15) — see MIGRATION-NOTES.md for the compatibility implications of each.

Done

  1. Statuses are Prisma enums. Member names match the previously stored strings, so nothing downstream changed. Surfaced six latent type errors.
  2. The cascade is fixed. evaluator and buyer are now SetNull, so deleting a reviewing admin or a winning vendor no longer deletes the tender and everything beneath it. owner keeps Cascade, where it is correct.
  3. The transition table is declared. src/v1/domain/tender-state.ts holds both machines; the five per-function guards call into it.
  4. The schema is indexed. Bids by tender and status, tenders by status with category and with deadline, notifications by user and read state, and the question/answer foreign keys. There were none.
  5. Notification ordering is uniform. closeTender and cancelTender now notify after commit, matching acceptBid.
  6. cost is now minimumBid, with @map("cost") so the stored field is unchanged, a response shim mirroring the old key, and DTOs accepting either. Existing clients are unaffected.
  7. Dead and loose fields tightened. hasNotification removed; email and password are now required.

Still open, deliberately

  1. Notifications remain fire-and-forget. Never awaited, failures logged rather than raised. That is the intended trade for a non-critical channel.
  2. Deadline expiry is still lazy — it runs opportunistically on read rather than on a schedule, so a tender nobody looks at stays open past its deadline. It belongs in a scheduled job.
  3. There are still no tests. The enum conversion was verified by the compiler and a build, which is not the same thing. The state-machine table is now a pure function over two enums — the natural first target.
Calibration This is the most disciplined backend of the set — real layering, thin controllers, centralised errors, transitions that check their preconditions, and an award path that gets atomicity, ordering, and side-effect placement all correct. The weaknesses were concentrated in the schema rather than the logic: statuses as strings, cascades that deleted too much, and no indexes. An unusual and rather encouraging shape for a defect profile — the hard part was done well and the declarative part was rushed, which is the opposite of how these usually fail. That schema work has since been done; what remains open is listed above.
